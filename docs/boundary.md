# Граница Sim: зеркало

Как Rust-симуляция встаёт рядом с `sim-ts` (`docs/engine.md`, §2 и шаг 9.4). Здесь — устройство границы,
синхронизация и порядок работ до первой системы на Rust.

## 1. Решение

**[решено, 2026-10-16]** Граница — нынешний интерфейс `Sim` (`packages/sim-ts/src/sim.ts`): хост, сеть и тесты
ходят через его поля — `world`, `land`, `vision`, `traces`, `deposits`, памяти, `send`, `advance`, `save`. Rust-симуляция
встаёт за тот же интерфейс через обёртку `RustSim` (`packages/sim-rust`), которая держит **зеркала**: TS-мир и
TS-объекты слоёв, совпадающие с состоянием Rust после каждого `advance`.

Почему так, а не узкая граница (команды, тик, кадры игрокам):

- **Тесты остаются.** 59 файлов тестов сами пишут в `sim.world` (634 места) и берут из `sim-ts` 267 имён. Переписать их на
  сценарный API — огромная работа до первой строчки логики на Rust. С зеркалом те же 596 тестов гоняются против обеих
  реализаций, и система Rust готова, когда они зелёные.
- **Хост не меняется.** Он собирает кадры игрокам из TS-мира: туман, приоритеты, сверка JSON компонентов
  (`host.ts`, `check`). С зеркалом это работает как есть; перенос рассылки в Rust — отдельный шаг потом.
- **Форма компонентов и так общая.** Сохранение (`WRLD`) и сеть — JSON компонентов TS. Rust всё равно обязан их
  читать и писать.

Отвергнуто:

- **Узкая граница сразу** — чище, но сначала переписать хост и ~600 тестов.
- **Тесты только у TS, Rust — сверкой** — быстрее начать, но 596 проверок Rust напрямую не проходит.

Цена зеркала: синхронизация на каждый тик (в проде — только из Rust в TS, только изменённое), Rust держит форму
TS-компонентов. Тесты, которые зовут TS-функции логики напрямую (`orderMove(sim, …)`, `findPath`), проверяют TS-логику
поверх зеркала, а не Rust; такие места помечаются по мере переноса.

## 2. Что зеркалится

| Поле `Sim` | Зеркало | Откуда в Rust |
|---|---|---|
| `world` | TS `World` с теми же номерами сущностей | журнал операций хранилища (§3) |
| `land`, `paving` | чанки земли и слой покрытия | изменённые чанки и тайлы по ревизии |
| `vision` | карты обзора игроков | изменённые клетки |
| `traces` | следы | новые и истёкшие |
| `deposits` | слой месторождений | по ревизии |
| `landMemory`, `paveMemory`, `buildMemory` | памяти игроков | выученное за тик |
| `occupancy` | занятость тайлов | считается в TS по зеркалу мира, как сейчас |
| `time`, `events` | как есть | после `advance` |
| `rules`, `online` | пишет хост | в Rust при записи |

Начало — мир; слои добавляются по мере того, как их системы переезжают (§4). Слои в Rust — единым механизмом
(`docs/layers.md`): у всех один формат изменений, и зеркало у них одно.

## 3. Синхронизация мира

**Журнал операций, а не набор изменённого.** Хранилище Rust повторяет TS-мир: номера сущностей, плотные массивы на
компонент, удаление перестановкой последнего, обход от самого маленького хранилища. Если обе стороны применяют одни
и те же операции в одном порядке — `spawn`, `add`, `set`, `remove`, `destroy`, — порядок обхода у них совпадает, а от
него зависят результаты систем.

- **Rust → TS.** После тика Rust отдаёт журнал: операции по порядку, данные компонента — JSON, ключи как в TS.
  Обёртка применяет его к зеркалу. Значение, которое Rust поменял на месте, попадает в журнал как `set` — Rust сам
  знает, что писал.
- **TS → Rust.** Запись через API мира (`spawn`, `add`, `set`, `remove`, `destroy`) ловит журнал TS-мира (новая
  необязательная подписка в `@kharos/ecs`). Правку на месте (`world.get(e, X)!.field = …`) журнал не видит: в тестах и в
  смешанном прогоне (§4) обёртка сверяет JSON компонентов с последним синхронизированным; в проде TS в мир на месте не
  пишет (хост пишет только через API).
- **Компоненты в Rust** сначала хранятся как JSON-значения: хранилищу их смысл не нужен. Типизированная структура
  (serde, имена полей как в TS) появляется у компонента, когда его читает первая система на Rust.

## 4. Смешанный прогон: перенос по системам

Порядок систем тика (`createSim`) — именованный список в `sim-ts` (`SimSystem`), его можно подменить крючком
`createSim(source, { systems })`. У `RustSim` каждая система из списка выполняется либо в Rust, либо TS-функцией из `sim-ts` поверх
зеркала; на каждой смене стороны внутри тика — синхронизация.

1. **Ноль систем в Rust.** Все системы — TS поверх зеркала, Rust только хранит мир. 596 тестов с `KHAROS_SIM=rust`
   проверяют само хранилище и синхронизацию.
2. **По системе.** Система переписывается на Rust и переключается в списке; тесты зелёные — следующая. Каждая
   перенесённая система сразу проходит все тесты в окружении остальных, а не ждёт конца переноса.
3. **Все системы в Rust** — синхронизация остаётся одна, после тика, и только в одну сторону. Это и есть прод-режим.

Смешанный прогон медленный (сверка JSON на каждой смене стороны) — он для тестов и разработки, не для игры.

## 5. Сборка и переключатель

- **wasm без связки.** `crates/sim-wasm` собирается `cargo build --target wasm32-unknown-unknown` и отдаёт плоские
  функции (выделить и освободить буфер, создать мир, применить журнал, тик, взять журнал). Данные — байтами через
  память модуля. Без `wasm-bindgen`: меньше инструментов, тот же подход, что у `luau.wasm`.
- **Тесты:** `KHAROS_SIM=rust bun test` — `packages/tests/setup.ts` подменяет `createSim` (`mock.module`) на `RustSim`.
- **Хост:** настройка сервера `sim` в `settings.json`, адрес страницы `?sim=rust`, переменная окна (`docs/engine.md`, §2).
- **Сверка:** инструмент гоняет обе симуляции на одних командах и сравнивает снимки, дробные — с допуском; печатает
  первое расхождение.
